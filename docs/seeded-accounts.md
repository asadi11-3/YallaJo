# YallaJo — Seeded Accounts, Roles, and Passwords

> **Internal developer reference.** This document describes accounts created
> automatically at application startup so the team can sign in during local
> development and Playwright tests. **Do not deploy this content publicly.**
>
> Generated by code audit on 2025-12 from the live source tree.
> Single source of truth: [`src/BuildingBlocks/YallaJo.SharedKernel.Infrastructure/Data/SeedIdentityProfiles.cs`](../src/BuildingBlocks/YallaJo.SharedKernel.Infrastructure/Data/SeedIdentityProfiles.cs).

## TL;DR

- **24 user accounts** are seeded automatically in two families.
- **All 16 production-family users** share the password **`P@ssw0rd!`** (domain `@yallajo.local`).
- **All 8 Playwright-family users** share the password **`TestPass!23`** (domain `@yallajo.test`).
- **8 roles** are defined in `AppRoles.cs`: `Owner`, `SuperAdmin`, `Admin`, `Provider`, `TourGuide`, `Creator`, `User`, `Guest`.
- Seeding runs only when `ASPNETCORE_ENVIRONMENT=Development` **or** `Seeding:Enabled=true` is set in configuration (see [`DataSeedingExtensions.cs:29`](../src/Hosts/YallaJo.Api/Extensions/DataSeedingExtensions.cs)).
- Role + permission seeding (`SecurityDataSeeder.SeedAsync()`) **always** runs at startup, regardless of environment.

## Roles

Defined in [`AppRoles.cs`](../src/Modules/Security/Security.Contracts/Authorization/AppRoles.cs) (lines 31–41).

| Role         | Privilege Level | Notes |
| ------------ | --------------- | ----- |
| `Owner`      | 100             | Singleton. In `ProtectedRoles` and `OwnerOnlyRoles`. Cannot be assigned by anyone but Owner. |
| `SuperAdmin` | 80              | In `ProtectedRoles` and `OwnerOnlyRoles`. Only Owner can promote a user to SuperAdmin. |
| `Admin`      | 60              | Standard administrator role; full access to the Admin area. |
| `Provider`   | 10              | Generic content provider tier. **No seeded user holds this directly** — users earn it via approved applications. |
| `TourGuide`  | 10              | Provider tier specialized to tour guides. |
| `Creator`    | 10              | Content/blog creator tier. **No seeded user holds this directly.** |
| `User`       | 10              | Standard traveler (default for new sign-ups). |
| `Guest`      | 10              | Anonymous fallback. In `DefaultRoles`. |

`AppRoles.AllRoles` = `[SuperAdmin, Admin, Owner, Provider, TourGuide, Creator, User, Guest]`.
`AppRoles.DefaultRoles` = `[Guest]`.
`AppRoles.ProtectedRoles` = `[SuperAdmin, Owner]`.
`AppRoles.OwnerOnlyRoles` = `[Owner, SuperAdmin]`.

## Seeding flow

```
Program.cs:306 → UseDataSeedingAsync()         (Dev OR Seeding:Enabled config flag)
                ├─ MigrateAsync on 14 DbContexts
                ├─ Order 30 → SecurityDbInitializer
                │             • 5 fixed-GUID role rows
                │             • All users from SeedIdentityProfiles.All (password hashed via IPasswordHasher.Hash)
                ├─ Order 40 → AuthDbInitializer
                │             • Devices, sessions, OTP records, refresh tokens for the seeded users
                ├─ Order 50 → AccountsDbInitializer
                │             • Profile aggregates for the seeded users
                └─ Order 51 → AccountsProviderApplicationSeeder
                              • 4 provider applications for guide-pending, guide-approved,
                                business, agency (test users 4–7)

Program.cs:316 → SecurityDataSeeder.SeedAsync()  (ALWAYS runs, not Dev-gated)
                ├─ SeedRolesAsync       → idempotent insert of every AppRoles.AllRoles
                ├─ SeedRoleClaimsAsync  → writes RoleClaims from RolePermissionMapping
                └─ AuditRoleClaimsAsync → audit-only drift report (no deletes)
```

## Security warnings — secrets committed to the repository

The credential audit also found these **production-grade secrets committed to `appsettings.json`**. They are not part of the user seeding, but they ship in the same checkout and **must be rotated before this repository becomes public or moves to a shared environment**.

| File:Line | Secret | Recommendation |
| --------- | ------ | -------------- |
| `src/Hosts/YallaJo.Api/appsettings.json:63-69` and `appsettings.Development.json:52-59` | Gmail App Password for SMTP sender `muhmooud2003@gmail.com` | **Revoke the Gmail app password now.** Move SMTP credentials to user-secrets / Key Vault. |
| `src/Hosts/YallaJo.Api/appsettings.json:34-41` | Google reCAPTCHA SiteKey + SecretKey | Rotate the reCAPTCHA secret in the Google Cloud console; move to config provider. |
| `src/Hosts/YallaJo.Web/appsettings.json:29-39` | Google OAuth ClientId + ClientSecret | Rotate in Google Cloud console; move secret out of repo. |
| `src/Hosts/YallaJo.Web/appsettings.json:29-39` | Facebook OAuth AppId + AppSecret | Rotate in Facebook Developer console; move secret out of repo. |
| `src/Hosts/YallaJo.Api/appsettings.json:26-32` and `src/Hosts/YallaJo.Web/appsettings.json:18` | ExternalAuth HMAC signing key | Generate a fresh random key per environment; move to config provider. |

**Recommended remediation steps:**

1. Move all of the above out of `appsettings*.json` into [.NET user-secrets](https://learn.microsoft.com/aspnet/core/security/app-secrets) for local development and Azure Key Vault / environment variables for hosted environments.
2. Add the original keys to a **rotation list** and rotate them at the upstream providers (Google, Facebook, Gmail).
3. Add a CI guard (e.g. `trufflehog`, `gitleaks`) that fails the build if a secret pattern is reintroduced into tracked files.
4. Rewrite Git history (`git filter-repo`) only if these secrets must be removed from the existing commit log before the repo is shared externally.

## Production hardening checklist

Before deploying to a non-development environment:

- [ ] Delete `SeedIdentityProfiles.All` entries or guard them with `IsDevelopment()` only (currently they leak into any environment that sets `Seeding:Enabled=true`).
- [ ] Change the shared passwords `P@ssw0rd!` and `TestPass!23` — they are now public in this repo.
- [ ] Confirm `Seeding:Enabled` is **not** set in `appsettings.Production.json` or in deployment environment variables.
- [ ] Rotate the secrets listed in the section above.
- [ ] Verify the `Owner` user has an MFA / hardware key enrolled before this account ever exists in production.
